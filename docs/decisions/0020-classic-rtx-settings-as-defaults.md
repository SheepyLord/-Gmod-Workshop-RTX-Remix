# 0020: The classic RTX install's settings are the package's defaults

- Status: Accepted 2026-10-29
- Decided by: the user ("all RTX-Remix setting in the addon should by default use the setting we
  already have in GarrysMod_RTX_c (record our setting as the default value)"), Claude choosing how.
- Builds on: [0008](0008-activation-at-startup.md) (config layers), [0010](0010-rtx-session-extras.md)
  (session console variables), [0013](0013-rtx-only-addons-hidden-without-rtx.md)

## Context

The field test showed the field install rendering differently from the user's classic RTX install
(`GarrysMod_RTX_c`): the player model in the first-person view, a fog-filled pool room, and a map
full of extra lights ([RESEARCH.md](../RESEARCH.md) section 19). The settings behind it live in two
places the package did not cover:

- **Remix's `user.conf`** in the classic install holds 91 settings that override its `rtx.conf`. They
  include the player-model texture list, the fog (volumetrics), atmosphere, light handling, the
  NRC mode and the Custom graphics preset. The package shipped the classic `rtx.conf` and `dxvk.conf`
  as layers, but not this.
- **The RTX add-ons' console variables**, which GMod keeps in `cfg/client.vdf` and `cfg/server.vdf`.
  - The classic install has the fixes' own `.vdf` values (RTXLauncher copied them into `cfg`) plus
    the user's tuning.
  - The package cannot write `cfg` (ADR 0014), so the field ran the Lua defaults instead. Examples:
    `rtx_pseudoplayer` 1 instead of 0, `rtx_api_map_lights_autospawn` 1 instead of 0,
    `rtx_lightupdater` 0 instead of 1, and custom water off.

## Decision

1. **Remix settings: the classic files merged into the package's defaults layer.** The classic
   `dxvk.conf`, `rtx.conf` and `user.conf` are merged, in the classic install's own precedence, into
   one layer below the player's files ([ADR 0021](0021-remix-defaults-in-one-low-layer.md)). What
   the player saves in the Remix menu wins.
2. **Add-on settings: first-run defaults in the companion.** The companion carries the classic
   values, generated by [`tools/classic_defaults.py`](../../tools/classic_defaults.py.md) from the
   classic `client.vdf` and `server.vdf`. It applies them once per table version and realm.
   - Only a setting still at its add-on's own default is changed (`ConVar:GetDefault()`). A value the
     player chose stays.
   - `nativeloader_rtx_defaults` applies every classic value on request.
   - Not session variables: those are set again at every RTX start, and would undo the player's
     changes each time.

## Consequences

- A new player gets the classic look on the first RTX start. A player who already changed a setting
  keeps it, and can take the classic values with one command.
- The defaults are tuned for the user's RTX 5090: the Custom preset, DLSS Quality and frame
  generation. Players on weaker GPUs change the preset in the Remix menu, and that choice persists.
- Raising the table's `version` hands the new values to every player once more, again only for
  settings at their defaults.
- The classic `user.conf` contains no paths or personal data. It ships only merged into the
  defaults layer, never as a file named `user.conf`, which the packager's private-file guard refuses.

## Alternatives considered

- **Session variables for the add-on settings.** They are reapplied every RTX start, so the player's
  menu changes would reset: the bug the user reported.
- **Writing the classic `client.vdf` into `cfg`.** That is the user's own settings file and outside
  the package areas (ADR 0014). It would also overwrite every other add-on's settings.
- **Changing the defaults in the fixes' Lua.** That is the GPL fork, and it would not reach installs
  that already saved the old defaults.
